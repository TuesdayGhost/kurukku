# くるっくー UI 設計・レビュー Skill（ドラフト v0.3）

## 前提として読むもの

- `docs/spec.md`（仕様。「希望」「決定」「提案」「未決」の区別を尊重する）と `docs/tasks.md`（実装状況）。
- このSkillは仕様を書き換えない。仕様の決定と規格がぶつかるときは、衝突として指摘し代案を出す（6章）。
- 過去のレビュー記録は `references/baseline-*.md`。**記録は当時の事実であり、今の事実ではない**（7章の手順0）。
- 「活版文字組みスキル」は spec 3章のとおり将来の制作補助。うまくいった組みの規則が出てきたら `typography.md` に足していく。

## 最上位の目的

> 忘れても、もう一度ここを見れば分かる。本人にも家族にも、余計な負担を増やさない。

すべての判断はこの一文に照らして説明する。「美しいから」「見やすいと思うから」だけでは決めない。
ただし美しさを否定しない。美しさは目的と衝突しない範囲で、積極的に残す。

## 1. 根拠の5段階（必ずラベルを付ける）

判断や指摘には、次のどれに基づくかを必ず書く。混ぜない。ラベルは**根拠の種類**であり、評価結果ではない（評価は2章）。

| ラベル | 意味 | 書き方の例 |
|---|---|---|
| **[R] 規格要件** | WCAG 2.2 の達成基準（A/AA）。JIS X 8341-3:2016 に同番号があれば併記 | 「[R] WCAG 2.2 SC 1.4.3（AA）／JIS 2016 同番号」 |
| **[R+] 採用した上位基準** | WCAG の AAA など、規格上は任意だが、くるっくーが**自分で採用を決めた**もの | 「[R+] SC 1.4.6（AAA）を本人用表示に採用」 |
| **[G] 補助的推奨** | W3C COGA、WAI の解説、JLReq、JIS S 系など、適合要件ではない指針 | 「[G] COGA 4.5.1」 |
| **[H] くるっくー仮説** | 利用場面から導いた設計仮説。資料の直接の要請ではない。**実機・本人で検証が必要** | 「[H] 1画面1話題にすると再確認が速い」 |
| **[P] 好み・美意識** | 作り手の好み。目的と衝突しない限り尊重する | 「[P] 活版の朱を差し色に」 |

禁止事項:
- [G][H][P] を「基準で決まっている」「規格上必要」と書かない。
- [R+] を [R] と書かない（AAA は「採用した」のであって「求められている」のではない）。
- 数値の出典が確認できないときは「要原文確認」と書き、数値を断定しない。
- **規格の条件・例外を省略して書かない。** 「〜は禁止」「〜とは両立しない」と書く前に、その達成基準の条件（例: 3秒を超える、他の内容と並行して表示）と、満たし方の選択肢（例: 停止・調整・無効化の仕組み）を原文で確かめる。規格が「仕組みを用意すれば可」としているものを、くるっくーが使わないと決めたなら、それは [H] か [P] の設計方針として書く。
- 仮の値から計算した結果は仮の値。式を通しても根拠は強くならない。

## 2. 判定は「何を・どこまで確かめたか」と分けて書く

レビュー結果は次の4列で出す。

| 列 | 入れるもの |
|---|---|
| **根拠** | 1章のラベルと出典（例: [R] 1.4.2） |
| **規格チェック**（[R][R+] のみ） | 合格／不合格／該当なし／判定保留 |
| **利用適合** | 良い／懸念あり／要改善／未評価 |
| **確認の段階** | 未確認／コード上の対応あり（挙動未確認）／実機で確認済み／本人の様子で確認済み |

ルール:
- **コードの特徴（属性・CSS）だけで「合格」にしない。** それは「判定保留＋コード上の対応あり（挙動未確認）」。合格にできるのは、達成基準が対象とする挙動を確かめたとき。
- 規格に合格していても、お父さんに使いにくければ「利用適合: 要改善」。規格外の工夫で使いやすくなっていても、規格の不合格は消えない。
- **個別項目の合格を、画面全体の合格に広げない。** 見ていない達成基準は「未確認」のまま残す（3章のチェック範囲）。
- 規格を満たさないと分かっていて、目的のために意図的にそうする場合は「**意図的な逸脱**」として、理由と代わりの配慮を書いて残す。黙って合格扱いにも、黙って直したことにもしない。

くるっくーは「JIS X 8341-3 準拠」等の**適合表明はしない**（試験手順を踏んでいないため）。規格は設計とレビューの根拠として使う。

## 3. 基準線とチェック範囲

- [R] **WCAG 2.2 レベル AA** を全画面の基準線とする。
  - 理由: 現行 JIS X 8341-3:2016 は WCAG 2.0 と一致。WCAG 2.2 は 2.0 の上位互換（4.1.1 削除を除く）で、ISO/IEC 40500:2025 と同一内容。JIS は ISO/IEC 40500:2025 との一致規格として改正作業中。
  - JIS 2016 に無い（2.1／2.2 で追加された）達成基準を挙げるときは「JIS 2016 には無い」と明記する。
- [R+] 画面ごとに一部 AAA を採用する（`references/screens.md`）。
- `references/sources.md` の「よく使う達成基準」は**入口であって全部ではない**。A/AA の全項目のうち、そのレビューで見ていないもの（キーボード操作 2.1.1、フォーカス順序 2.4.3、フォーカスが隠れない 2.4.11 など）は、判定表の末尾に「未確認」としてまとめて書く。
- 端末ごとの操作手段を前提にする: 父の部屋のタブレットはタッチのみ、居間の Yoga 3 はキーボード・マウスあり、家族はスマホ。キーボード操作の確認は居間と家族画面を優先する [H]。

## 4. 画面プロファイル（要約）

詳細は `references/screens.md`。レビュー前に該当画面のプロファイルを必ず読む。

| 画面 | 使う人・状態 | 最優先 | 典型的な失敗 |
|---|---|---|---|
| 本人用表示（通常・通知・夜） | 父。操作しない。何度も見返す。画面によく触る | 見ればいつも同じ場所に同じ種類の答えがある。通知は予測できる形で来て、静かに戻る | 予定が黙って切れる、止められない音声、読めないほど小さくして全件を詰める |
| 家族用操作（スマホ・居間） | 家族。忙しい・片手・短時間。居間は90秒で戻る | 少ない手数、保存が分かる、やり直せる | 保存されたか分からない、入力が予告なく消える、入力欄が見えない |
| レスキューカード | 焦っている家族が、警察・近所に見せる／電話で読む／送る | 顔写真と体格がすぐ出る、そのまま伝わる | 奥にある、単位や測定日がない、画像だけで文字がない |
| 鳩月報 | 本人と家族。月に一度、ゆったり | 笑えて、写真と見出しから思い出せる | 見出しを画像化、写真上の文字が読めない、予定を実績のように書く |

**出力の形を分ける。** 同じ画面でも、Web画面・共有する画像・印刷物では確かめることが違う。レスキューカードの共有画像は仕様で決定済みなので常に見る。印刷（カード・月報）は仕様上「余力で判断」なので、実装されたときだけ `field-checks.md` の印刷の項目を使う。

## 5. レビューの観点（7軸）

各軸で「その画面のプロファイル」に照らして確認する。代表的な根拠は `references/screens.md` と `references/typography.md`。

1. **文字**: 大きさ（実機の実寸と視距離を測って確認）、書体、行送り、字詰め、表記（日付・時刻・呼び名）。**読める下限を下回らない**
2. **余白**: まとまりの境界、行間・段落間、1.4.12 の文字間調整で崩れないか
3. **配置**: 重要情報の位置の固定、一貫性、スクロールなしで見えるか。入りきらないときに何が起きるか
4. **色**: コントラスト比（計算値を書く）、色だけに頼らない、写真上の文字
5. **音**: 自動で鳴る音はどれか・何秒か（1.4.2 の3秒）。止める手段または独立した音量調整が、**その画面を使う人から**届くか。音だけに頼らない
6. **画面切り替え・自動更新**: 時刻での切り替え、時計・天気・予定の自動更新（2.2.2）、時間制限（2.2.1）、動き、予期しない移動
7. **操作**: ターゲットサイズ、キーボード操作（居間・家族）、誤操作の防止と取り消し、入力の重複、認証、保存のフィードバック

## 6. 提案が原則と衝突したとき

作り手（葵依）の提案や仕様の決定が原則や利用目的と衝突する場合:

1. 衝突を指摘する。どの根拠（ラベル付き）とどう衝突するかを、達成基準の条件・例外まで含めて書く。
2. 衝突の強さを区別する: [R] との衝突は「修正が必要（または意図的な逸脱として記録）」、[G][H] との衝突は「懸念・要検証」。
3. **提案の意図**（例: 懐かしさ、紙の質感、新聞の見出しの迫力、放置されたら父の画面に戻したい）を言葉にして残す。
4. 意図を残したまま衝突を解く代案を、少なくとも1つ出す。代案が規格を満たすかどうかは、**満たすために確かめる条件**と一緒に書く（「この案で満たせる」と先に断定しない）。
5. 規格への対応と、生活上の使いやすさの対応は、別の項目として書く（例: 時間制限の延長手段と、下書きを残すこと）。
6. 好み同士・仮説同士の対立は、どちらかに決めつけず、実機・本人確認の項目にする。
7. 制約の中で解けない対立（例: 全件を見せたいが、読める大きさでは入らない）は、自動の処理で解決済みにせず、**表示方針の衝突として報告**し、葵依に判断を返す。

## 7. 手順と出力形式

手順0（毎回）: 対象のブランチとコミットを確かめて冒頭に書く（例: `git rev-parse --short HEAD`）。過去の baseline と違うコミットなら、baseline の判定は「当時の記録」として参照するだけにし、見直していない項目は「未確認」に戻す。

```
## 対象: <画面名> / <コンポーネント or 変更内容>
対象コミット: <branch> @ <hash>（前回記録: baseline-YYYY-MM-DD @ <hash>）

### 判定
| # | 観点 | 指摘 | 根拠 | 規格チェック | 利用適合 | 確認の段階 |
|---|------|------|------|--------------|----------|------------|

未確認の達成基準: …（このレビューで見ていない A/AA 項目）

### 意図的な逸脱（あれば）
- 達成基準: … / 理由: … / 代わりの配慮: … / 見直す条件: …

### 衝突と代案
- 提案: …
  - 意図: …
  - 衝突: … [R]/[G]/[H]（条件・例外まで）
  - 代案: …（規格を満たすために確かめること: …）

### 実機・本人で確かめること（`references/field-checks.md` から、今回の変更に関係する2〜3項目だけ）
- [ ] …（何を、どう観察すれば判断できるか）

### 計測値・計算値
- コントラスト: 前景 #xxxxxx / 背景 #xxxxxx = n.n:1
- 文字の実寸: 端末 … で、要素 … が 高さ約 … mm（定規で測定）／普段の視距離 約 … cm
```

## 8. 範囲の制限（ハッカソン期間）

- 調査は `references/sources.md` の資料に限る。追加するときは、今の実装の判断が変わる場合だけ。
- 迷ったら「仮説として実装し、確認項目に書く」。調べ続けて止まらない。
- **家族の確認負担を増やさない。** `field-checks.md` は候補集。1回のレビューで頼む確認は、今回の変更に関係する2〜3項目まで。
- 本人を「検査」しない。確認は普段の利用の様子を見ることを基本にする。読み上げや見比べなどの短い確認は、本人が嫌がらないときだけの任意とする。本人の気持ちと同意を優先する（[G] COGA 5.3 Informed Consent）。
