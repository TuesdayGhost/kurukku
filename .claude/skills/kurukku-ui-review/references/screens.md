# 画面プロファイル

各画面について「誰が・どんな状態で・何をするか」から、適用する根拠と仮説を決める。
高齢者を一括りにせず、**その画面を使う場面**で判断する。
前提は `docs/spec.md`（v0.6）と `docs/tasks.md`。仕様と食い違ったら仕様を優先し、このファイルを直す。

端末（spec 2章 決定 11/3）
- 父の部屋：Androidタブレット（Headwolf FPad3）、Chrome。表示専用＋アプリ固定。父はよく触る。
- 居間：Lenovo Yoga 3（Windows・Firefox）。表示が基本、家族が簡単追加。90秒で表示に戻る。
- 家族：スマホ（Android／iPhone）。

## 1. 本人用表示（通常画面・通知画面・夜表示）

**場面**: 父が、日付・天気・時計・本人と家族の今日の予定・家族の知らせを、操作せずに何度も見返す。
（spec v0.6・11/4 決定）ふだんの画面にはその日の大事な予定（デイ・家族の外出など）だけを出し、ごはん・お薬はお知らせのときだけ出す。終わった予定は消す。本人の予定は開始の時刻だけ、行事などは「小さく添える一言（20文字まで）」として2行目に出す。天気はふだん最高・最低気温まで。予定の時間帯になると、鳩が鳴き、読み上げ、通知画面に切り替わり、終了で戻る。夜（初期値21時〜6時）は暗い配色で時計と「夜です」。父は画面によく触る。

### 採用する基準
- [R] WCAG 2.2 AA 一式
- [R+] SC 1.4.6 コントラスト（高度）— 通常画面・通知画面・夜表示の本文。大きな文字は 4.5:1、それ以外は 7:1
- **採用しない（今回は）**: SC 3.2.5 要求による変化（AAA）。
  - 原文は「利用者の要求によってのみ変化する」か「そのような変化を無効にする仕組みがある」のどちらかを求める。したがって通知画面への自動切り替えと**両立不能ではない**（無効にする仕組みを用意すれば満たせる）。
  - 全画面の通知への切り替えが「コンテキストの変化」に当たるかは確認が要る。Understanding はコンテキストの変化に「内容の大幅な組み替え」を含めているので、当たる可能性が高い（判定保留）。
  - 採用しない理由は [H]: この端末では、時刻での切り替えが知らせる役目そのもの（spec 3章）で、父に無効化を任せる場面がない。代わりに下の「予測できる切り替え」で配慮する。

### 衝突と代案：通知の音声と SC 1.4.2（判定保留）

**11/4 対応**：代案Aを採用・実装（確認の段階: コード上の対応あり・挙動は偽の接続先のブラウザで確認、実機未確認）。通知画面に見て分かる「音を止める」ボタンを鳴っている間だけ出す。画面のどこを触っても止まる動きも残す。居間のキーボードでは Esc でも止まる。チャイムと読み上げの両方を止め、順番待ちの残りも鳴らさない。止めても通知画面と予定は残る。重複防止の記録は鳴らす前に付けるので、止めた通知が再び鳴ることはない。父が触って止めてしまう副作用は実機で見る（葵依：父が驚いて怒らないよう、触ると止まるほうがよい）。
- 設計: 開始時にチャイム2回＋「くるっくー。ぽーちゃんです。お父さん、6時半から夕ごはんです。」（spec 3章）。
- 衝突: 合計で3秒を超える見込み。1.4.2 は、自動再生が3秒を超える音声に「一時停止・停止の手段」または「システム音量と独立した音量調整」を求める [R]（A、JIS 2016 にもあり）。
- 意図: 本人に確認操作を求めない（設計方針1）。鳩が知らせ、あとは静かに置く。
- 代案A（規格への対応の候補）: 通知画面に「音を止める」手段を置く。止めても通知画面と予定はそのまま。止めるのは任意で、確認操作ではない。
  - 満たすために確かめること:
    - 止め方が**見て分かる**か（画面のどこを触っても止まるだけでは、気づけない。目に見える止めるボタンか表示を置く）
    - チャイムと読み上げの**両方**が止まるか（ブラウザの読み上げ `speechSynthesis.cancel()` とチャイムの再生を両方止める）
    - タッチ以外（居間の Yoga 3 のキーボード）でも止められるか [R] 2.1.1
    - 止めたあと、同じ通知で再び鳴らないか（spec 3章の重複防止と整合）
  - 父の「よく触る」とは相性がよい可能性がある。触って止めてしまい気づかない副作用は実機で見る [H]。
- 代案B（生活上の配慮）: 家族設定に、端末ごとの「お知らせの音量」（アプリ内の音量、ゼロも可）を置く。
  - **これだけでは 1.4.2 の根拠にしない。** 1.4.2 の仕組みは、その音が鳴っている画面を使う人が使えるものを指すと読むのが自然で、別の端末の家族だけが操作できる設定は、本人画面の適合の根拠として弱い（Astra 査読、原文の意図＝音が他の音を聞く妨げになる人のため）。
  - 音量の好み・夜の音量などには有効。代案Aと併用する。
- 原文の補足: Understanding 1.4.2 は、音の自動再生そのものを勧めていない（利用者が始めるほうがよい）。くるっくーは知らせることが目的なので自動で鳴らすが、その分、止める手段と短さで配慮する。読み上げ文を短くして3秒以内に収める案も、文言の分かりやすさとのトレードオフとして検討できる [H]。

### 自動更新と SC 2.2.2（11/4 葵依が決定：記録を閉じる）

**決定（11/4）**：
- **時計**は「不可欠」の例外として扱う。時刻を表示することが機能そのもので、止めると機能が変わるため。この解釈は原文で直接は確かめていない意図的な判断として記録する（[H]）。
- **天気・予定・知らせの自動更新**は「意図的な逸脱」として記録する。
  - 達成基準: 2.2.2（A）
  - 理由: 父に更新の停止を任せる場面がなく、止めると情報が古くなる。「もう一度見れば分かる」には、表示が今の情報であることが前提
  - 代わりの配慮: 更新しても位置を変えない、動きを付けない、天気は取得できないときに古さを表示する、接続できないときは最終更新の時刻を出す
  - 見直す条件: 本人や家族が、更新による変化で戸惑う様子が見られたとき
- 以下は判断の前の検討（当時の記録）。

### （検討の記録）未解決だったとき：自動更新と SC 2.2.2
- 事実（コード）: 時計は毎秒、天気は30分ごと（失敗時5分）、予定と知らせはリアルタイム購読と定期再読込で更新される（`app/app.js`）。
- 規格: 2.2.2 は「自動で始まり、他の内容と並行して表示される自動更新の情報」に、一時停止・停止・非表示か、更新頻度の調整の仕組みを求める。ただし更新が「不可欠」な活動の一部なら例外。Understanding は天気・ニュースなどを自動更新の例に挙げ、時計については個別に論じていない。
- くるっくーの意図: 「もう一度見れば分かる」には、表示が今の情報であることが前提。古い予定のまま止まっていることのほうが害が大きい [H]。
- 選択肢（どれにするかは葵依が決める）:
  1. **時計を「不可欠」の例外として扱う**（時刻を表示するという機能そのもので、止めると機能が変わる）。この解釈は原文で直接は確かめられていないので、意図的な判断として記録する。
  2. 天気・予定には、家族側から更新頻度を設定できる仕組みを置く（天気は既に30分固定）。ただし代案Bと同じく、本人画面の利用者が使える仕組みではない点は残る。
  3. 本人画面について「意図的な逸脱」として記録する（理由: 父に更新の停止を任せる場面がなく、止めると情報が古くなる。代わりの配慮: 更新しても位置を変えない、取得時刻を出す、動きを付けない）。
- 適合表明はしないので、2.2.2 を理由に今の更新の仕組みを変える必要はない。ただし「合格」とは書かない。

## 2. 家族用操作（スマホ・居間）

**場面**: 家族が通勤中・家事の合間にスマホで予定や知らせを入れる。居間では Yoga 3 で簡単追加し、90秒で表示に戻る。母が使える簡単入力（家族→用件→時刻→追加）が目標。

### 採用する基準
- [R] WCAG 2.2 AA 一式。JIS 2016 に無い 1.4.10, 1.4.11, 2.5.8, 3.3.7, 3.3.8, 4.1.3 を特に見る

### 7軸への反映

| 時間制限（規格） | 居間の90秒復帰は、内容が設ける時間制限。2.2.1 は例外に当たらない限り、次のどれかを求める: 前もって解除できる／前もって既定の10倍以上の幅で調整できる／切れる前に知らせ、20秒以上の猶予と簡単な操作で延長できる（10回以上） | **[R] 2.2.1**（下の「衝突と代案」） |

### 衝突と代案：居間の90秒復帰と SC 2.2.1（判定保留）

**11/4 対応**：代案を実装（コード上の対応あり・偽の接続先のブラウザで、時計を早送りして確認。実機未確認）。最後の操作から65秒で「まもなく表示の画面に戻ります　あと○秒［続ける］」を出す（猶予25秒）。「続ける」（キーボードでも押せる）か、画面のどこかを操作すれば延長、何度でも。90秒で表示に戻る。入力途中の下書き保存は未実装（spec では保存方式は未決。勝手に登録はしない）。
- 意図: 居間で放置されたら、父も見られる表示画面に戻したい（spec 2章）。この意図は守る。
- 「途中の入力が消えることを事前に分かるようにする」だけでは 2.2.1 の対応にならない（Astra 査読、原文で確認）。
- 代案（規格への対応の候補）: 戻る**20秒前**に「まもなく表示に戻ります」と出し、「続ける」を押せば延長できる。延長は何度でも。Understanding も、キオスク端末では無操作のとき「まだいますか」と尋ね、続けるならその前の状態にそのまま戻すことを述べている。
  - 満たすために確かめること: 知らせが入力中の画面の上で見えるか、20秒以上あるか、キーボードでも「続ける」を押せるか、延長後に入力内容とフォーカスが元のままか。
- 代案（生活上の配慮・別項目）: 表示に戻っても、入力途中の内容を下書きとして残し、次に開いたとき「書きかけがあります」と出す。勝手に登録はしない。
- 延長の知らせが出ている間に、父が居間の画面を見たときに戸惑わないかは実機で見る [H]。

## 3. レスキューカード（父が戻らないときに、家族がすぐ出す）

**場面**: 父が外出先から戻らない。焦っている家族が、警察や近所の人に**画面を見せる**、電話で**読み上げる**、写真と情報を**送る**（spec 5章 決定 11/3）。読む・聞く相手は初めて父を知る人。本人の常設画面には出さない。

### 採用する基準
- [R] WCAG 2.2 AA 一式
- [R+] SC 1.4.6 コントラスト（屋外・明るい場所で他人に見せるため）
- [R+] SC 2.5.5 ターゲットのサイズ 44px（入口のボタン・共有ボタン。焦った指で押すため）

### 7軸への反映
| 軸 | 方針 | 根拠 |
|---|---|---|
| 文字 | 顔写真・身長・体重・靴のサイズをいちばん目立たせる | spec 5章 決定 |
| 文字 | 不確かな数字は「約165cm（2026年11月に測定）」。空欄より「約」＋測定日 | spec 5章 決定 |
| 文字 | 単位を省かない（「165」でなく「約165cm」）。電話で読み上げたときにそのまま伝わる語順 | [H]／[G] COGA 4.5.12 |
| 配置 | 1画面で、写真→体格→服装候補→その他の順に、スクロールが少なくて済む並び | [G] COGA 4.3.1, 4.6.2／[H] |

- [H] よく着る服の候補は、写真だけより「紺のジャンパー」のような一言があるほうが電話で伝えやすい。

## 4. 鳩月報（スポーツ新聞風に、その月を笑って振り返る）

**場面**: 月に一度、本人と家族が眺める。大見出しと写真が中心の家庭新聞（spec 7章）。平凡な出来事を大げさに報じる可笑しさが大事。くるっくーの美意識をいちばん出せる画面。

### 採用する基準
- [R] WCAG 2.2 AA 一式
- 1.4.6（AAA）は採用しない。見出しは大きな文字なので AA の 3:1 が下限、本文は 7:1 を目標 [H]

### 7軸への反映
| 軸 | 方針 | 根拠 |
|---|---|---|
| 文字 | 大見出しは**実テキスト**で組む。スポーツ紙の迫力は太い書体・字送り・大小差で出す | [R] 1.4.5 |
| 文字 | 写真ごとに短い説明。脚色した見出しと別に、元の出来事も分かるように | [R] 1.1.1／spec 7章（元の記録を残す） |

## 文字サイズの決め方（全画面共通の手順）

数値は資料で決まらない。**測る→使う様子を見る→調整する**の順で決める [H]。

1. 実機（父の部屋の Headwolf FPad3、居間の Yoga 3）で、日付・時計・予定の文字の実寸（高さ mm）を定規で測る。今の本人画面は `vmin` と `clamp()` で決めているので、端末ごとに実寸が違う。
2. 父が普段その画面を見る位置からの距離を、だいたいで測る。
3. 普段の暮らしの中で、読めているか・目を細めていないか・近づいて見ていないかを観察する（`field-checks.md`）。
4. 調整したら、実寸と距離を判定表の「計測値」に記録する。次のレビューで比べられるようにする。
5. 読める下限として確かめた実寸を記録し、「収めるための縮小」はそれを下回らない（本人用表示の配置の項）。

参考（任意）: 視角から文字高を求める式 h = 2 × D × tan(θ/2) は、端末を変えるときの見当づけに使える。ただし採用する視角 θ の根拠がないうちは、結果も仮の値として扱う。JIS S 0032 は原文未入手の参照候補として保留し、必須の手順に入れない。
